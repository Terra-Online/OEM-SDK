# 第一批补测：性能与体积报告

## 结果解读

- 第一批代码已提交为 `ddcba3b`，其源码快照指纹与本次 `batch1` 完全一致；基线为 `55fcb1a`。
- 标准嵌入 gzip 增加 **1,840 B（2.50%）**，主要用于请求生命周期、资源状态和失败恢复；CSS 未改变。
- 人为将边界元数据延迟 200 ms 时，初始化中位数 **278.2 → 70.4 ms**，验证了后台预加载不再阻塞创建。
- 普通初始化 **73.5 → 70.3 ms**、10k 自定义点初始化 **645.1 → 646.2 ms**，没有据此宣称 CPU 渲染显著提速。大点位的全量重建成本仍然存在。
- React 初次自定义点请求由 **2 次降至 1 次**；第一批收益主要是避免重复工作及等待，而非改换渲染算法。

## 比较口径

- 快照：`baseline`（SHA-256 `9dfcffcb86e872b10bc8293d9e2e2c6858376c097add64b0702d1f1d6a37602c`）；`batch1`（SHA-256 `21dd65c90289727f12806924071a52b703259f0b883a5795c638ebd098300b7a`）。
- darwin 25.6.0 arm64；Apple M2 Pro；Chrome 152.0.7977.83；Node v25.9.0。
- 每个场景每版 15 次有效样本，另各预热 2 次；交替执行版本，每次使用新的浏览器上下文。计时为实际无头 Chrome，不是 jsdom。
- 本机 HTTP 固定数据，960×640 地图；不加载瓦片或字体网络资源。标准元数据含 1,024 顶点的边界，标签场景含 200 个标签；custom 场景按名称提供点数。200 ms 场景只延迟点击推断的边界元数据，用于验证初始化是否等待它。并非线上 CDN 延迟预测。
- 初始化从调用 `createOEMWidget()`／React render 起，到创建返回／`onReady` 为止；不计调用前的 JS 模块下载。paint 为随后两帧完成的时间，仅表示绘制机会，不保证所有外部图像完成。
- JS 体积为 esbuild 生产压缩、ES2022、ESM 分块后的所有 JS 块之和，包含 Leaflet、聚合与输入依赖；React 场景的体积排除宿主 React。gzip level 9／Brotli quality 11 分块压缩后求和，排除 source map。CSS 单列。
- 小幅耗时差异可能是计时噪声；样本 p95 是经验分位值，不作为性能保证。用后堆增量包含模块／浏览器缓存，不能据此认定泄漏。

## 复现与原始数据

```sh
node scripts/bench/snapshot.mjs baseline 55fcb1a
# 在第一批／第二批对应 checkout 中分别保存快照；已存在的快照不会被覆盖。
node scripts/bench/snapshot.mjs batch1 ddcba3b
node scripts/bench/prepare.mjs baseline batch1
node scripts/bench/run.mjs baseline batch1
node scripts/bench/report.mjs measurements-baseline-batch1.json batch1
```

使用本机安装的 Google Chrome；`BENCH_SAMPLES` 可覆盖默认 15 次。快照位于被 git 忽略的 `artifacts/benchmarks/snapshots`。原始样本及摘要随本报告保存，包含失败检测、每次请求数及快照指纹。
